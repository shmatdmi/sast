# Тестирование

Проект использует встроенный `node:test`, без дополнительных тестовых зависимостей.
Для воспроизведения проверок используйте Node.js 24 и `npm ci`.

## Команды

| Команда | Что проверяет | Требования |
| --- | --- | --- |
| `npm run test:unit` | Все модульные тесты движка, правил, ZIP, JSON, паролей, языков, Sonar Lite и каталога | Node.js |
| `npm test` | Production-сборка, серверный HTML и доступ к API без авторизации, затем модульные тесты | Node.js |
| `npm run test:coverage` | Покрытие исходных модулей `app/lib/*.ts` и `scripts/lib/*.mjs` | Node.js |
| `npm run test:integration` | Production-сборка и API с настоящей временной PostgreSQL | Node.js и Docker |
| `npm run check` | ESLint и `npm test` | Node.js |
| `npm run test:all` | `check`, затем весь интеграционный набор API | Node.js и Docker |

`scripts/test-unit.mjs` автоматически находит новые файлы `tests/*.test.ts`
и `tests/*.test.mjs`. Тесты серверного HTML запускаются после сборки.
Файлы `*-db.test.mjs` и `*.integration.test.mjs` выполняются отдельно,
поскольку требуют базы данных.

## Интеграционные сценарии

Проверяются первоначальное создание администратора, нормализация логина,
ошибки входа, безопасные cookie, истечение и отзыв сессий, logout,
разграничение ролей, создание и удаление пользователей, блокировка,
смена роли, временный пароль, аудит и смена постоянного пароля.
Пароль из 7 символов принимается, из 6 и 257 символов отклоняется.
Повреждённый scrypt-хеш не позволяет войти с произвольным паролем.

Для SAST проверяются выполнение анализа через JSON и ZIP, все шесть новых
языков, сохранение и чтение находок, поиск истории, неверные поля,
лимиты размера, небезопасные пути и откат транзакции при ошибке сохранения.
Для Sonar Lite проверяются сохранение метрик и находок и валидация отчётов.
Health endpoint проверяется при доступной и недоступной базе.
Авторизованный HTML проверяется на охват 20, минимальную длину пароля
и ту же версию, которую возвращает API.

`scripts/test-api.mjs` всегда создаёт собственный контейнер `postgres:17-alpine`
со случайными именем, паролем и портом на `127.0.0.1`. Данные находятся
во временной файловой системе, контейнер удаляется после завершения.
Значение `DATABASE_URL` из пользовательского окружения не используется.
Внутри контейнера выполняются настоящие миграции таблиц пользователей
и результатов сканирования. Сборка импортируется как серверный обработчик;
проверяются реальные маршруты и транзакции без mock-замены запросов к БД.

Каталог правил использует отдельные существующие DB-тесты:
`npm run test:rules-db` и `tests/coverage-rule-db.test.mjs`.
Они требуют специально подготовленной тестовой базы и не включены в
автоматически создаваемую базу API, чтобы не дублировать импорт
150 036 определений при каждом запуске.

## Как читать покрытие

Контрольный прогон на Node.js 24: 1 060 модульных тестов, 12 тестов
серверного HTML/API и 29 интеграционных тестов API. ESLint прошёл.
Для исходных модулей отчёт показал 100% строк, 94,44% ветвей и 99,15% функций.
`auth-crypto.ts`, `scan-json.ts` и `sonar-lite.ts` имеют 100% по всем трём
показателям; у `sast-engine.ts` — 85,71% ветвей, у `archive.ts` — 81,58%.

Отчёт `test:coverage` относится к загруженным исходным модулям анализа и
каталога, а не ко всему приложению. API проверяется отдельно на собранном
сервере, поэтому процент покрытия исходных маршрутов из этого отчёта
не следует выводить. Большой объём декларативных правил увеличивает общий
процент строк; смотрите также ветви и функции в каждом модуле.

Проверки HTML не заменяют интерактивные браузерные E2E-тесты. В этом наборе
нет автоматизации кликов, загрузки через файловый диалог и визуальных снимков.
