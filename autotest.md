# Автотесты CodeSentry

## Зачем приложению нужны автотесты

Автотест — это программа, которая запускает часть приложения с заранее подготовленными данными и сравнивает полученный результат с ожидаемым. Если кто-то изменит правило безопасности, обработку ZIP или серверный рендеринг, тесты помогут обнаружить поломку до публикации приложения.

Автотесты решают несколько задач:

1. Проверяют, что уже реализованные функции продолжают работать.
2. Описывают ожидаемое поведение приложения на конкретных примерах.
3. Упрощают проверку новых правил и исправлений.
4. Делают изменения предсказуемыми: после правки можно быстро проверить основной сценарий.

Тесты не доказывают отсутствие абсолютно всех ошибок. Они проверяют выбранные сценарии. Поэтому набор следует пополнять при исправлении каждого дефекта и при добавлении нового поведения.

## Что проверяется

В проекте 20 автоматических тестов: 19 функциональных тестов библиотек и один интеграционный smoke-тест production-сборки.

| Область | Что проверяется |
| --- | --- |
| SAST-движок | Определение языка, правила разных языков, номера строк и столбцов, фрагменты кода, CWE-ссылки, оценка риска |
| Потоки данных | Прохождение пользовательского ввода в SQL-запрос и остановка потока после явной валидации |
| Безопасные случаи | Исключения для примеров секретов, безопасной загрузки YAML и constant-time сравнения |
| ZIP-архивы | Поддерживаемые расширения, сортировка файлов, игнорируемые каталоги и бинарные файлы, path traversal, повреждённый или слишком большой архив |
| Несколько файлов | Суммарный результат, пути файлов и определение нескольких языков |
| Production-сборка | HTTP-статус, Content-Type, основной HTML, русский интерфейс и Open Graph-изображение |

Новые проверки находятся в `tests/additional.test.ts`. Команды запуска добавлены в `package.json`. Дополнительные библиотеки не потребовались: тесты используют встроенный `node:test`, а ZIP создаётся уже установленным `fflate`.

## Типы тестов в проекте

### Функциональные тесты библиотек

Эти тесты вызывают функции напрямую, без браузера и сети:

- `tests/sast-engine.test.ts` проверяет основной набор правил;
- `tests/archive.test.ts` проверяет распаковку ZIP;
- `tests/additional.test.ts` проверяет граничные случаи, языки, структуру результата, потоки данных и auth-правило.

Такие тесты работают быстро. Например, тест передаёт движку строку `eval(value)` и проверяет наличие правила `JS001`.

### Интеграционный smoke-тест

`tests/rendered-html.test.mjs` запускается на собранном production-приложении. Он вызывает Cloudflare Worker как HTTP-обработчик и проверяет возвращённый HTML. Это короткий smoke-тест: он не имитирует все действия пользователя, но подтверждает, что главная страница собирается, отвечает без ошибки и содержит ключевые элементы интерфейса.

Перед ним команда `npm test` выполняет `npm run build`. Поэтому тест также обнаруживает ошибки TypeScript, сборщика, React-компонентов и серверного рендеринга.

## Как устроен тест

Обычно тест состоит из трёх частей, известных как Arrange, Act, Assert:

1. Arrange — подготовить входные данные.
2. Act — вызвать тестируемую функцию.
3. Assert — сравнить результат с ожиданием.

Простой пример:

```ts
test("обнаруживает eval", () => {
  const result = scanCode("eval(value)", "app.js");
  const ids = result.findings.map((finding) => finding.ruleId);
  assert.ok(ids.includes("JS001"));
});
```

Если `JS001` найден, тест проходит. Если изменение движка случайно отключит это правило, `assert.ok` завершится ошибкой, а Node покажет имя теста и место несовпадения.

Хороший тест изолирован: он не зависит от порядка запуска других тестов, не обращается к случайным данным и проверяет один понятный сценарий.

## Как запускать

Установить зависимости (требуется только при первом запуске или после их изменения):

```bash
npm install
```

Собрать приложение и выполнить полный набор:

```bash
npm test
```

Успешный итог должен содержать `pass 20`, `fail 0` и код завершения 0.

Запустить функциональные тесты библиотек с отчётом о покрытии:

```bash
npm run test:coverage
```

Выполнить линтер, сборку и все тесты одной командой:

```bash
npm run check
```

Команда `npm run check` подходит для локальной проверки перед commit или отправкой изменений.

## Как читать отчёт о покрытии

Отчёт показывает, какая часть исходного кода была выполнена тестами:

- line coverage — покрытие строк;
- branch coverage — покрытие вариантов условий, например веток `if/else`;
- function coverage — покрытие функций.

Высокий процент полезен, но не гарантирует качество проверок. Строка может выполниться без проверки правильности результата. Поэтому важны сценарии с осмысленными ожиданиями: опасный и безопасный ввод, граничные размеры, повреждённые данные, несколько файлов и настоящий HTTP-ответ.

Текущий отчёт измеряет покрытие модулей `archive.ts` и `sast-engine.ts`. Production HTML отдельно проверяется smoke-тестом.

## Что делать, если тест не прошёл

1. Найти имя упавшего теста и первую строку его стека.
2. Сравнить `expected` (ожидалось) и `actual` (получено).
3. Запустить тест ещё раз, чтобы исключить случайный сбой.
4. Если изменилось требуемое поведение, осознанно обновить код и ожидания.
5. После исправления повторно выполнить `npm run check`.

Не следует просто удалять неудобную проверку. Сначала нужно понять, обнаружила ли она дефект реализации или устаревшее ожидание.

## Как добавлять новые тесты

При исправлении ошибки добавляйте сценарий, который воспроизводит её до исправления и проходит после него. Давайте тесту конкретное имя, используйте минимальные входные данные и проверяйте наблюдаемый результат. Затем запустите как минимум `npm run test:coverage`, а перед завершением работы — `npm run check`.
